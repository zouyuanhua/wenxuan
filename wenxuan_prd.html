问玄 · 产品需求文档

心有惑，一卦问玄 —— 基于周易卦象的 AI 问事应用

版本：v1.0  |  日期：2026-10-31  |  小组：神机营

1. 产品概述

1.1 一句话定义

问玄是一个面向所有人的 AI 卦象问事应用：用户写下困惑、摇卦六次，即可获得基于《周易》原文、由 AI 生成的白话解读与可执行建议——引文全部来自典籍数据库，绝不编造。

1.2 要解决的问题

现状痛点解法
人工算命门槛高、价格贵、质量参差不齐AI 标准化解卦：结构化输出、低成本、随时可用
套壳 AI 算命排盘常错，术数逻辑靠模型瞎算排盘由确定性代码完成（起卦/纳甲/变卦 100% 准确），LLM 只负责把结果讲成人话
AI 解读引用的"古籍原文"多为编造，不可验证接入 64 卦典籍数据库，解读引用的卦辞爻辞逐字来自注入的原文，并在卦卡上展示供用户核对
用户要的不是"预测未来"，而是决策参考与情绪出口定位文化娱乐：给趋势判断 + 可执行建议，明确非宿命论断言
传统术数脱离当代语境（古人问求官，今人问 offer）"古卦今译"分类体系：8 大类 30+ 现代场景问题模板，一键填入

1.3 目标用户

用户角色核心诉求使用频率 / 付费意愿
决策焦虑的都市白领（25-35）换工作、感情、重大消费抉择时，需要一次郑重其事的参考仪式每月 1-4 次 / 中（单次付费可接受）
在校学生（18-24）考试、升学、恋爱困惑，想要有趣的自我探索中高频 / 低（社交传播为主）
传统文化爱好者对周易卦象有兴趣，希望有严谨的排盘与原文低频 / 高（愿意为深度内容付费）

1.4 产品愿景

让每一次迷茫都有一场郑重其事、有典可依的对话——把《周易》变成当代人用得起、信得过的决策陪伴。

1.5 产品边界

本期做：

· 问事台（分类/子项模板/疏文）+ 摇卦（六爻纳甲规则）+ AI 解卦（典籍 grounding）+ 追问循环（3 次上限）

· 双端交付：H5/Web（含预览服务）+ 微信小程序

本期不做：

· 登录注册、会员支付、社区、真人解卦师入驻、塔罗/八字、每日运势

明确声明：本产品为传统文化娱乐应用，不预测命运，不提供医疗/法律/投资/婚姻专业建议，不提供付费改运消灾服务。

2. 用户故事与使用场景

2.1 核心用户故事

故事 1

作为 面临换工作抉择的上班族，我想要 摇一卦并获得结合我所问之事的白话解读，

以便 在犹豫不决时获得一份有《周易》原文背书的参考，把心里的大石头变成可执行的小步。

故事 2

作为 对解读仍有疑问的用户，我想要 就同一卦象继续追问（最多 3 次），

以便 把困惑挖得更深，而不必重新起卦、丢失已有的卦象上下文。

故事 3

作为 解卦服务本身（AI 角色），我想要 只依据服务端注入的《周易》原文进行解读，

以便 杜绝编造卦辞爻辞的幻觉，让每一条引文都可以被用户核对。

2.2 核心使用流程

Step 1: 问事台        — 选分类、抽子项签（或自由来问），写下心事（5-200 字）
Step 2: 诚心已备      — 疏文焚化转场，问题与分类锁定
Step 3: 摇卦          — 三枚铜钱轻摇六次，逐爻升起，得本卦与变卦
Step 4: 解卦          — 服务端查典籍数据库，AI 生成五段式白话解读（引文逐字可核对）
Step 5: 追问          — 同卦最多追问 3 次；超限收尾"此卦已尽，建议心定后另择时再问"

2.3 典型使用场景

场景 A：offer 抉择

1. [用户] 手里两个机会犹豫不决，睡前打开了问玄

2. 选「事业-求职面试」，模板自动填入"这个 offer 我能拿到吗?"，摇得天山遁、初爻动

3. 系统给出解读，引用初九爻辞"潜龙，勿用"，建议先蛰伏观察、暂不表态

4. 结果：用户追问"时机"，获得"待时机"的趋势判断与三条可执行建议，安然入睡

3.2 P0 功能详述

F1：问事台（FR-01）

一句话描述单屏完成"选分类 → 抽子项签 → 疏文确认"的三步问事，全程入戏微文案
输入点选 8+1 分类之一；点子项签自动填入问题模板（可编辑）；或自由输入文本
处理逻辑分类必选且选定后锁定；问题 5-200 字（码点计数）；模板填充与自由编辑并存；更换分类清空疏文并提示"再想想，换一事来问"
输出合法的 {分类, 问题} 交给摇卦流程；氛围条按节气展示文案
异常处理未选分类/空问题/不足 5 字/超 200 字分别给出入戏提示（"心事未落笔，如何起卦?"等）+ 抖动 + 震动，且不起卦
依赖utils/ask-data.js（分类/签语/文案数据源）
验收标准单屏完成三步、无跳页、首用到确认 ≤10 秒；A.4 微文案零系统腔；三种校验均拦截；分类锁定后无更换入口

F2：摇卦（FR-02）

一句话描述三枚铜钱轻摇六次，逐爻升起得本卦/动爻/变卦，概率与手工摇钱完全一致
输入用户点击铜钱（小程序支持后续扩展摇一摇）
处理逻辑3 枚独立硬币各 50/50；一背二字=少阳、二背一字=少阴、三背=老阳(动)、三字=老阴(动)；六爻自下而上；动爻阴阳翻转推变卦；64 卦 King Wen 表查名
输出结构化六爻数据（coins/name/yang/moving）+ 本卦/变卦描述（卦序号/全名/卦符/上下卦）
异常处理引擎未加载提示刷新；单爻失败还原重试；非法钱象抛错
依赖hexagram 引擎（Web/小程序/Python 三方同源）
验收标准5 万+爻模拟分布与理论值偏差 ≤1%；64 卦名全量核对通过；同种子结果完全可复现；古籍卦例（乾→姤、乾全动→坤等）回归通过

F3：AI 解卦（FR-03/04，典籍 grounding）

一句话描述服务端重算卦象 → 注入 64 卦典籍依据 → LLM 生成五段式白话解读，引文逐字可核对
输入{question, lines:[{coins}×6], followup?}
处理逻辑服务端 classify_coins 重算卦象（不信任前端术数）→ 按卦 id 查 64gua.json 构建【典籍依据】（本卦卦辞/大象 + 动爻爻辞/小象 + 变卦卦辞）→ system=提示词+典籍依据（追问时追加同卦约束），user=JSON 数据 → DeepSeek 生成 → 完整性校验
输出五段式解读（卦象直读/核心矛盾/趋势判断/行动建议×3/典籍引证，400 字内）+ 免责声明 + 卦辞摘要（前端展示）
异常处理上游超时 60s→504 可重试；响应不完整/超长→拒绝；API Key 永不回显；典籍库缺失→优雅降级为无 grounding
依赖DeepSeek API；src/config/64gua.json；prompt.json（系统提示词）
验收标准免责声明 100% 附带；解读引文必须逐字来自【典籍依据】；趋势方向不得与服务端规则结论相悖；排盘数值全部来自服务端重算

F4：追问循环（FR-05）

一句话描述对同一卦象最多追问 3 次，多轮对话仍受典籍依据与同卦上下文约束，超限温和收尾
输入{followup: {index:1..3, question ≤200字, history:[{question,answer}]}}（前端持有历史，服务端无状态）
处理逻辑校验模块统一校验（轮次/一致性/长度/结构）→ 构建多轮 messages（原始卦象 → 历史问答对 → 本次追问）→ system 追加同卦约束指令
输出与首答同构的追问解读；前端以【追问n】形式追加展示
异常处理第 4 次或 history≥3 → 400"此卦已尽，建议心定后另择时再问"；index 与 history 不一致→400 刷新提示；空追问→入戏提示
依赖F3 解卦管线；followup.py 校验模块（前后端共用）
验收标准3 次内正常应答且回答与原卦象自洽（回归：乾初爻动→姤）；第 4 次请求 400 且文案为收尾语；追问不改变卦象与动爻

F5：合规与安全护栏（NFR-04）

一句话描述免责声明 100% 附带 + 敏感输出过滤 + API 密钥隔离
输入所有 AI 输出与用户请求
处理逻辑免责声明服务端/前端双层固定附；疾病/投资/法律指令场景只给一般性思路；安全响应头（CSP/nosniff）；密钥仅存服务端 .env 且响应中扫描拦截
输出合规的可发布内容
异常处理命中敏感场景→改写为一般性建议并提示求证专业渠道
依赖无
验收标准抽样 100 条解读：免责覆盖率 100%、零绝对化断言、零专业指令

4. 技术架构

4.1 技术选型

层级技术选型理由
前端框架原生 HTML/JS/CSS；微信原生小程序零构建链、双端覆盖；问事/摇卦交互不依赖重框架，便于审核与长期维护
UI/样式手写 CSS/WXSS（纸墨主题，CSS 变量）视觉资产（卦符/阴阳爻线）为自绘，无需组件库；与"入戏"微文案体系配套
后端框架Python FastAPI + uvicorn农历/干支生态（lunar-python）成熟；与 AI 调用同语言；异步支持断连取消
数据库P0 无（卦象 JSON 全量落库为规划）；典籍库为 JSON 文件无个人数据存储，先验证需求；知识库以文件版本化，Git 即审计日志
AI/模型DeepSeek Chat API（thinking 关闭，max_tokens 2200）中文术数语料熟悉度高、成本可控；模型与提示词均配置化
部署本地 uvicorn / 单机部署；发布需 HTTPS 域名P0 以本地与内测为主；小程序正式版要求 HTTPS 合法域名
其他关键依赖freizl/yijing 64gua.json（典籍数据）；lunar-python（规划：干支）；微信开发者工具典籍原文是防幻觉基石；干支转换是纳甲装卦前置

4.2 系统架构草图

用户浏览器 (H5) / 微信小程序
  │  POST /api/interpret {question, lines[6]{coins}, followup?}
  ▼
FastAPI 后端 (app.py)
  ├── canonicalize：输入校验 + classify_coins 服务端重算卦象（本卦/变卦/动爻）
  ├── 知识检索层：gua_classics.py → 64gua.json 构建【典籍依据】
  ├── 追问校验：followup.py（轮次/一致性/长度，前后端共用）
  └── LLM 编排：system=提示词+典籍依据(+同卦约束)；user=结构化卦象 JSON
  │
  ▼
数据 / 外部服务
  ├── config/64gua.json   ：64 卦卦辞/彖/大小象/爻辞（防幻觉基石）
  ├── config/prompt.json  ：系统提示词（PromptStore 运行时可调，原子写）
  └── DeepSeek API        ：生成解读（60s 超时、断连取消、响应上限校验）

4.3 核心数据流

用户操作: 摇满六爻，点击「解卦」
  │
  ▼
前端: POST /api/interpret {question, lines:[{coins}×6]}   ← 只送铜钱面，不送术数结论
  │
  ▼
后端: classify_coins 重算六爻 → 本卦/变卦/动爻 → 查 64gua.json 构建【典籍依据】
  │   → system = 提示词 + 典籍依据（追问时再追加同卦约束与历史问答）
  ▼
DeepSeek: 依据典籍原文生成五段式解读
  │
  ▼
后端: 完整性/长度/密钥泄漏校验 → 返回 {interpretation, classics, hexagram}
  │
  ▼
前端: 展示解读 + 卦卡下方并排展示典籍卦辞原文（可核对）→ 追问面板开启（剩余 3 次）

4.4 关键设计约束

1. 术数计算只允许确定性代码完成；LLM 禁止重新起卦、改写卦名/动爻/阴阳，禁止计算任何术数结果。

2. 解读引用的卦辞/爻辞/象传必须逐字来自注入的【典籍依据】；免责声明必须 100% 附带于每次解读。

3. API 密钥只存服务端 .env，绝不下发前端、绝不在响应或日志中回显。

4. 一问一卦：追问不重新起卦，始终基于同一卦象；上限 3 次。

5. 数据模型

5.1 核心实体

// 爻：一次摇掷的结果（前端/后端共用结构）
interface CastLine {
  coins: ("back" | "front")[];   // 三枚钱币面，back=背面
  name: "少阳" | "少阴" | "老阳" | "老阴";
  yang: boolean;                 // 本爻阴阳（true=阳）
  moving: boolean;               // 是否动爻（老阳/老阴）
  backCount: 0 | 1 | 2 | 3;      // 背面数
  marker: "" | "○" | "×";        // 动爻标记
}

// 卦象描述：服务端重算后的只读结果
interface HexagramDescription {
  number: number;                // King Wen 卦序 1-64
  name: string;                  // 短名，如"同人"
  fullName: string;              // 全名，如"天火同人"
  symbol: string;                // Unicode 卦符 ䷀..䷿
  upper: { name: string; nature: string };  // 上卦，如 乾/天
  lower: { name: string; nature: string };  // 下卦
}

// 解卦请求/响应
interface InterpretRequest {
  question: string;              // 原始问题（服务端限 1-2000 字）
  lines: { coins: ("back"|"front")[] }[];   // 恰好 6 爻，自下而上
  followup?: {                   // 缺省=首次解卦
    index: 1 | 2 | 3;
    question: string;            // ≤200 字
    history: { question: string; answer: string }[];  // 前几轮追问问答
  };
}

interface InterpretResponse {
  interpretation: string;        // 五段式解读 + 免责声明
  model: string;
  hexagram: { primary: HexagramDescription; changed: HexagramDescription; movingLines: number[] };
  classics?: { primary: { guaCi: string; daXiang: string }; changed: { guaCi: string; daXiang: string } | null } | null;
}

// 典籍条目（64gua.json，防幻觉知识库）
interface GuaEntry {
  id: string;                    // 自下而上阴阳二进制串，如 "101010"=既济
  name: string;                  // 卦名，如"既济"
  gua_ci: string;                // 卦辞
  tuan_ci: string;               // 彖辞
  da_xiang: string;              // 大象传
  yao_ci: string[];              // 爻辞[0..5]=初爻..上爻，[6]=用九/用六
  xiao_xiang: string[];          // 小象传
  symbol: string;
}

5.2 数据关系

· 一次问事会话 与 卦象 是 1 对 1 关系（一问一卦，追问不改卦）

· 一次会话 与 解读 是 1 对 1..4 关系（首答 + ≤3 次追问）

· 卦象 与 64gua.json 典籍条目 是 n 对 1 查询关系（本卦/变卦各查一条）

6. 非功能性需求

6.1 性能

指标目标值测量方法
解卦接口响应 (P95)≤ 15 秒（LLM 生成；后续流式可更早出首屏）服务端计时埋点（收到请求→返回响应）
首屏加载 (LCP)≤ 1.5 秒（静态页，无外部字体/脚本依赖）Lighthouse / DevTools Performance
摇卦动画流畅度≥ 30fps，翻转期无卡顿掉帧DevTools FPS 仪表 / 真机目测
摇卦随机分布每爻四结果与理论值偏差 ≤ 1%（5 万样本）种子化模拟统计（engine/tests 已实现）

6.2 可用性

浏览器兼容：Chrome / Edge / Safari 最新两个大版本；微信小程序基础库 ≥ 3.0

语言支持：简体中文（P0）；文案体系已按"入戏微文案"标准化，便于后续多语言

降级策略：典籍库缺失→跳过 grounding 仍可解卦；AI 服务不可用→友好错误+重试；系统"减少动态效果"→全部动画降级；音效可一键关闭

6.3 安全性

要求实现方式
用户认证P0 免登录（无账号体系，无个人数据收集）；P1 如增加历史云同步再引入微信授权
数据隔离无个人数据落库；问事记录仅存于用户本地（规划）
API 密钥保护仅存服务端 .env；响应与日志双重扫描，密钥永不回显；prompt 编辑端点默认仅本机（待加固项已登记）
传输加密开发期本地 HTTP；发布切换 HTTPS；响应统一 no-store + CSP/nosniff 等安全头

6.4 可靠性

上游 LLM 超时 60 秒→504 可重试；用户中途断连→取消上游任务避免浪费；响应不完整（finish_reason≠stop）→拒绝并提示重试；典籍数据库缺失或损坏→优雅降级（无 grounding 解读）而非崩溃；所有服务端异常不向用户泄漏内部诊断信息。

9.1 技术风险

风险影响缓解策略

10.2 术语表

术语定义
问事用户就某一具体困惑发起的一次占问；一事一占
摇卦三枚铜钱摇六次逐爻成卦的起卦方法；一背=少阳、二背=少阴、三背=老阳(动)、三字=老阴(动)
动爻老阳(○)/老阴(×)爻，代表变化点，解卦的核心依据
本卦 / 变卦摇卦所得原始卦 / 动爻阴阳翻转后的卦，分别代表现状与趋势
用神六爻分析中代表所问之事的六亲（官鬼/妻财/父母/兄弟/子孙），按问事分类映射
典籍依据服务端从 64gua.json 检索并注入 LLM 的《周易》原文块，是解读的唯一合法引文来源
疏文用户写下心事的文本载体，确认后以"焚化"动画封存
